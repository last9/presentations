Required baseline

What is an agent?

An LLM in a loop that takes actions, keeps state, and acts in the world, not a chatbot, not RPA.

the gate That approve? step is today's talk: how to make it precise and durable.
THE ONE IDEA

Approval is a declared policy, not ad-hoc code.

Each tool declares how much human it needs. The engine enforces it. The agent can't talk its way past it.

OWASP calls this least agency: bound what each tool can do, how often, and where.

The principle has a name now: OWASP's "least agency", which extends least privilege to agents, it constrains not just what an agent can access but what each tool can do, how often, and where. The key design choice: approval is declared on the tool, enforced by the engine, so the agent can't argue its way around it. Transition: why bother gating at all? Because the agent will be tricked.
Why a gate at all

It obeys, even attackers.

Meta's account-recovery bot changed emails and passwords on request. Attackers asked, and took over accounts: a White House one, Sephora, a Space Force official.

That's the confused deputy: a trusted agent using power it shouldn't wield alone. And via prompt injection, one poisoned GitHub issue is enough to do the asking.

Two ways a gate-less agent burns you, and they compound. One, the confused deputy: Meta's account-recovery bot would change an account's email and password on request, attackers just asked, and took over high-profile accounts. The bot had power it should never have wielded on its own. Two, prompt injection: one poisoned GitHub issue can be the thing doing the asking, no human needed. Simon Willison's lethal trifecta, private data + untrusted content + an exfil path, means agents are exposed by design. Transition: so "just add a human" should work, except the naive version backfires.
But the naive fix backfires

"Approve everything" trains people to click yes.

200 prompts a day and your team rubber-stamps them. Approval fatigue is its own vulnerability.

a gate everyone ignores is not a gate.

Structural control · per-tool approval levels

The tool declares how much human it needs.


TOOLS = [
  {"name": "get_metrics",          "human": "none"},     # read-only: auto
  {"name": "update_ticket",        "human": "approve"},  # write: one click
  {"name": "change_instance_state","human": "confirm"},  # destructive: type to confirm
  {"name": "run_command",          "human": "dynamic"},  # decide from the args
]

Irreversible ops use static confirm, never dynamic: a bug in your resolver can't downgrade a delete.

approvals gate the action. input spotlighting hardens the prompt, a complementary control we don't do yet.

Structural control · scale without fatigue

Memoize decisions; defend in depth.

Learned approvals

Decisions are memoized by a hash of the tool input. Approve the same call 3 times with zero denials (approval_auto_promote: 3) and it stops asking. Review or revoke any pattern.

Two locks, not one

engineer9 can stop an EC2 instance (approval) but the IAM role omits TerminateInstances and is tag-scoped. If the gate fails, IAM denies. If IAM is loose, the gate asks.

Identity is a boundary too

The day the agent said "I'm mithai."

engineer9's prompt never named it, so onboarding introduced it to a customer by the framework's name.

Not a break-out, the model followed the prompt exactly. Fix: explicit identity + an llm_judge eval that fails if the agent ever claims the wrong name.

DEMO

One destructive tool. One memoized one.

A confirm-level delete blocks for type-to-confirm. A read repeated 3× auto-promotes and stops asking.
