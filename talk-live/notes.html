The problem
5

Cold open — the incident

screen: Meta's account-recovery bot changed a user's account email. "It just needed to be asked."

Open cold, no throat-clearing. Real and recent — June 2026, reported by Malwarebytes. Meta's account-recovery bot would change an account's email when asked, which routed the password-reset code to the attacker (accounts with 2FA were safe). It just needed to be asked. Let that land for a beat. (Source: Malwarebytes, June 2026.)

6

Cold open — the lesson

screen: mechanics + victims · "the bot wasn't hacked…"

Walk the mechanics fast: geo-matched with a VPN, started a normal password reset, asked the bot to change the email, collected the one-time codes. Name the victims for stakes (a White House account, Sephora, a Space Force official). The spine of the whole talk: the bot wasn't hacked — it did exactly what it was told, with power it should never have wielded on its own judgment. The fix isn't a smarter prompt; it's enforcing the boundary below the agent. → so what IS an agent, and why does this keep happening?

7

What is an agent?

screen: the agent loop diagram · It's a code-execution system.

Define it so no one's lost: an LLM in a loop that takes actions, keeps state, and acts in the world — not a chatbot, not RPA. Walk the loop once: event → LLM → proposes → approve? → execute → tool → result, with memory underneath. The line that matters: the moment it can call tools, it stops being an "AI feature" and becomes a code-execution system. That reframe is the whole talk. → and whose code is it running?

8

Whose code is it?

screen: LLM-generated · third-party · customer-authored

Three sources, all untrusted: the model writes code at runtime, unreviewed; third-party skills you can't fully audit; tenants bring their own onto shared infra. The reframe: the code's ORIGIN changed — one sentence from a webhook now does what used to take a supply-chain compromise. → so we'll just guard the prompt, right?

9

"We'll add guardrails to the prompt."

screen: prompt = instruction, tool call = syscall · "you can't contain a running process with English"

The seductive wrong answer. A prompt is an instruction that runs before the model decides to misbehave; a tool call is a syscall, and once code is running the prompt is a suggestion. Concrete proof: Chipotle's bot got talked into writing code, and the analyst's takeaway is literally our thesis: enforce scope at the product level, not just the prompt. → so what's the one idea that has to hold?

The one idea
10

Thesis — structural, not conventional

screen: Isolation must be structural, not conventional. · the test: impossible, or just tedious?

The whole talk in one line — say it slowly. Structural means the guarantee lives BELOW the agent, in a layer it can't reach: the crypto, the DB key, the kernel. Conventional means a rule in the agent's own code we hope it follows. Then give them the take-home test: does this control make the attack IMPOSSIBLE, or just TEDIOUS? A rate limit is tedious; a separate kernel is impossible. Prefer removing a capability over throttling it. → let's watch a hostile agent try six things, and judge each defense by that test.

The six attacks
11

Six things a hostile agent will try

screen: the threat table · "we assume the code is hostile, and run it anyway"

The map for the next stretch. Don't read the table — name the three columns: what it tries, why that's plausible, what stops it. Each attack abuses a different thing (a secret, the CPU, the budget, the deploy, its own authority), each with a different structural control. The line that matters: we assume the code is hostile and run it anyway — nothing about the guarantee depends on the code behaving. → one at a time.

12

Attack 1 · "I'll read secrets that aren't mine."

Set the scene, then pause. Secrets live everywhere an agent can reach — env vars, files, process memory, even old snapshots. On shared infra it goes hunting for keys it was never handed. Let the threat sit, then flip to the defense.

13

Defense 1 · Encrypted to one identity

Every secret is encrypted to one identity — Argon2id→AES-256-GCM, bound to (workspace, agent) at construction. Reach the store all you want, it's ciphertext you can't even NAME, let alone decrypt; and the sandbox stops it reading a neighbor's env or memory. Apply the test: this removes the capability — impossible, not tedious. → next, it stops reading and starts running.

14

Attack 2 · "I'll run my own program."

It can write to its own dir, so it drops a native binary and execs it — now it's arbitrary machine code, outside whatever language runtime we thought we'd sandboxed. Flip to the defense.

15

Defense 2 · Landlock — writable, not executable

Landlock — a kernel LSM. The agent's dir is writable but NOT executable; system paths are read-exec only; it sees /proc/self, not its neighbors. A launcher applies Landlock, then execs the agent — the kernel refuses the exec no matter how clever the code is. Honest beat: plant the flag — "but it's still a shared kernel." We hit that ceiling at the end.

16

Attack 3 · "I'll take the whole box down."

Runaway compute — a different resource from spend. A bug or a hostile loop forks without end, or just never returns. On shared hardware that starves every other tenant: the noisy neighbor. Flip.

17

Defense 3 · One process group per agent

Each agent is its own OS process group (Setpgid). Stop is a hierarchical SIGTERM→SIGKILL of the whole tree — the runaway and every child it spawned die together. A crash or fork storm stays inside one agent. If asked about hard CPU/mem quotas: that's the separate-kernel / microVM layer at the end.

18

Attack 4 · "I'll burn $50k in a retry loop."

Different resource again — money. An agent stuck in a tool-error loop can spend more in an hour than the team spends in a month. Quick beat, then flip to the gate.

19

Defense 4 · Check the budget before the call

Check the budget BEFORE the call. Hard cap blocks; soft cap downgrades the model (Opus→Haiku). Atomic per-(workspace, agent, model) counters in micro-USD integers — no float drift. Blocked before a single token is spent. The test: a hard cap removes overspend; a rate limit only slows it.

20

Attack 5 · "I'll slip bad code in through your deploy."

Different stage — ingress, not runtime. Skills ship via a git webhook, so the attacker poisons the pipeline BEFORE the agent ever runs: spoof the webhook, smuggle a ../ path or a symlink, plant a setuid binary. Flip to the defense.

21

Defense 5 · Every push is treated as hostile

Treat every push as hostile: HMAC-verify the webhook, reject ../ traversal and symlinks, strip setuid/setgid (mode & 0755), cap size and file count. And the deploy is atomic — write a new version dir, flip a symlink; it fully lands or nothing changes, and rollback is one more flip. Verified, sandboxed, reversible.

22

Attack 6 · "A webhook told me to. So I did."

The subtle one — the confused deputy. The agent isn't hacked, it's CONVINCED. A poisoned email, page, or ticket injects an instruction and it acts with its OWN authority. Call back to the open: this is exactly the Meta bot. Flip to the defense.

23

Defense 6 · Least agency

You can't fully stop injection — so don't fight that battle. Constrain what it CAN do. Every skill declares its tools and credentials up front; sensitive actions are deny-by-default, needing explicit approval, never the agent's own judgment. A hijacked agent still can't invoke a capability it was never given. Injection changes what it WANTS, not what it CAN do — that's OWASP "least agency." → and every one of these attempts is on the record.

The boundary + the name
24

Tamper-evident audit

screen: per-workspace SHA-256 hash chain · "what did it do, and can you prove it? Yes"

The cross-cutting layer. Every attempt — success or failure — is on the record, tamper-evidently: a per-workspace SHA-256 hash chain, each event hashing the one before. Tamper one row and the chain breaks. Append-only, batched, partitioned. "What did it do, and can you prove it?" Yes. → now, why not just a container?

25

Why not just a container?

screen: 457 syscalls vs ~5 emulated devices · the isolation ladder

The objection everyone has. Namespaces change what a process SEES, not what the kernel DOES. ~457 syscalls reachable from a container (Docker's default seccomp blocks ~49); a separate-kernel microVM exposes ~5 emulated devices. runc escapes land yearly — CVE-2019-5736 through the Nov-2025 trio — and AWS's own advisory says it does not consider a container a security boundary. That Landlock ceiling I flagged earlier? This is it. → so what actually holds?

26

The boundary that holds

screen: separate kernel per tenant · Firecracker · "and you can buy the same thing"

The honest pivot. Landlock was real work and holds against a lot, but it's hardening a kernel the agent still shares — the ceiling is the kernel itself. Apply the test: a separate kernel makes escape impossible, not tedious. The good news: you don't have to build it. Firecracker boots in ~125ms, restores in single-digit ms, no confirmed guest→host escape in production. Anthropic runs Claude Code itself on Firecracker — proof you can buy this layer. → now put the whole system together — every gate in one picture.

Seed for the next talk
29

From one agent to a multi-tenant fleet

screen: control plane → tenant lanes of µVM agents (the unit, ×many)

The zoom-out, and a deliberate teaser. The architecture was the UNIT — one secured agent in a micro-VM. The platform is thousands of them: a control plane (the gate, scaled) that schedules micro-VMs, mints authorizations, meters spend, and keeps the record — partitioned per tenant, with per-VM quotas for density and the VM in the tenant's own cloud for residency. Multi-agent = agents that collaborate, every cross-agent call mediated by the gate. The hard parts — scheduling at scale, warm-pool economics, agent-to-agent trust, a signed skill marketplace, fleet-wide attestation — are a whole other talk. Say it as a seed: "that's where this goes." → but the one idea to take home —
